# AI4HF Passport — Backend (`passport`)

Spring Boot REST API for the AI Product Passport. Java 21, Spring Boot 3.2.2, Maven, PostgreSQL 16, Keycloak 24.

The frontend lives in the sibling repo `../passport-web`; workspace-level and cross-repo concerns are in
[`../CLAUDE.md`](../CLAUDE.md). Read that too before making domain changes — nearly every entity change
requires a matching frontend change.

## Engineering approach

Development phase — no backward compatibility required (see [`../CLAUDE.md`](../CLAUDE.md)):
- Schema changes: edit the DDL and seed data in `docker/deployment/init-db.sql`, then recreate the DB
  (`docker compose down -v`). No `ALTER TABLE` upgrade scripts, no dual-column transition states.
- API contract changes may break freely, as long as `passport-web` and the Postman collection are
  updated in the same change.
- Simplest implementation that meets the requirement: no new `application.properties` entries unless a
  value genuinely varies per deployment, no speculative interfaces or extra DTO layers, no indirection
  for future needs. Reuse the existing 4-layer pattern as-is.

## Layout

```
src/main/java/io/passport/server/
  Passport.java              # @SpringBootApplication entry point (note: same name as the Passport entity)
  config/                    # KeycloakProvider, KeycloakResolverConfig, KeycloakSecurityConfig
  controller/                # 33 @RestController classes, one per resource
  model/                     # JPA entities + composite-key classes + DTOs + enums
  repository/                # Spring Data JPA interfaces
  service/                   # business logic, cascade validation, Keycloak, PDF, signature
  util/JSONUtil.java
src/main/resources/
  application.properties     # all config; dev secrets committed here
  keystore.p12               # PAdES signing key (dev) for mvn spring-boot:run
docker/deployment/
  keystore/keystore.p12      # the same key, mounted into the passport container
  init-db.sql                # authoritative DDL (lines 1–~390) + demo data seed (rest, ~616 KB)
  realm-import.json          # Keycloak realm, client, roles
  docker-compose.yaml        # keycloak, both postgres instances, passport, passport-web
docs/passport.postman_collection.json
docs/architecture/           # component overview of the whole system, with its figures
docs/data-model/             # ER diagrams, generated from init-db.sql by generate_er.py
```

There is **no `src/test`**. See the workspace guide for how changes are verified.

## Build & run

```bash
mvn clean package -DskipTests
```

```bash
mvn spring-boot:run
```

The app needs Keycloak and PostgreSQL running (`docker/deployment/docker-compose.yaml`) and a fresh
`keycloak.credentials.secret` in `application.properties` after every realm re-import.

Notable properties: `spring.jpa.hibernate.ddl-auto=update` (additive only — no migration tooling),
`pdf.page.width/height/dsf`, `pdf.concurrent.renders`, `pdf.render.timeout.ms`, `pdf.chrome.executablePath`,
`dss.keystore.path/password`.

## The four-layer pattern

Every resource follows the same shape. Copy an existing quartet rather than inventing structure —
`ModelController`/`ModelService`/`ModelRepository`/`Model` is the canonical example, and
`FeatureDatasetCharacteristic*` is the canonical composite-key example.

### Entity (`model/`)

```java
@Entity
@Table(name = "snake_case_table")
@Getter @Setter                                  // Lombok; @AllArgsConstructor/@NoArgsConstructor where needed
@JsonIdentityInfo(generator = ObjectIdGenerators.PropertyGenerator.class, property = "<idFieldName>")
public class Foo {
    @Id
    @GeneratedValue(generator = "uuid")
    @GenericGenerator(name = "uuid", strategy = "uuid2")
    private String fooId;                        // String UUIDs everywhere, never numeric IDs

    @Column(name = "study_id")
    private String studyId;                      // FK held as a plain String, NOT a @ManyToOne
    ...
}
```

Conventions that matter:
- **No JPA relationship mappings.** Foreign keys are plain `String` fields; joins are written explicitly in
  `@Query`. Do not introduce `@ManyToOne`/`@OneToMany` — the cascade-validation machinery and the DTO layer
  both assume flat entities.
- IDs are `VARCHAR(255)` UUIDs generated by Hibernate, except `Personnel.personId` and
  `Organization.organizationId`, which are **Keycloak user/group IDs supplied by the caller**.
- Audit columns, where present: `createdAt`/`createdBy`/`lastUpdatedAt`/`lastUpdatedBy` (`Instant` +
  personnel id). Services set the timestamps; the frontend sets the `*By` fields from session storage.
- Composite keys use a separate `@Embeddable` `<Entity>Id` class and `@EmbeddedId`.
- DTOs (`*DTO.java`) are hand-written projection/aggregation classes, often built by JPQL constructor
  expressions in the repository.

### Repository (`repository/`)

`extends JpaRepository<Foo, String>`, derived query methods (`findByStudyId`, `findByModelId`), plus `@Query`
for joins. Two conventions are load-bearing:
- `findByCreatedByOrLastUpdatedBy(personnelId)` — used when deleting personnel.
- `findStudyIdByFooId(fooId)` — resolves the owning study, sometimes through several joins
  (e.g. `Dataset` → `Population` → `Study`).

### Service (`service/`)

Holds the repository, plus `RoleCheckerService` when it participates in cascade validation. Timestamps are
stamped here (`save*` sets `createdAt`+`lastUpdatedAt`; `update*` sets `lastUpdatedAt`). `update*` methods
**copy fields explicitly** onto the loaded entity — when you add a field to an entity you must add it to the
corresponding `update*` method or it will silently never persist on edit.

### Controller (`controller/`)

```java
@RestController
@RequestMapping("/foo")
public class FooController {
    private final String relationName = "Foo";                    // used in audit logs
    private final List<Role> allowedRoles = List.of(Role.DATA_SCIENTIST);   // write authority
    ...
}
```

Every mutating endpoint does, in order:
1. `roleCheckerService.isUserAuthorizedForStudy(studyId, principal, allowedRoles)` → `403` if false.
   (`StudyController` and `PersonnelController` instead use `hasAnyRole(...)`, since no study exists yet.)
2. Delegate to the service.
3. `auditLogBookService.createAuditLog(principal.getSubject(), principal.getClaim(TokenClaim.USERNAME.getValue()), studyId, Operation.CREATE|UPDATE|DELETE, relationName, recordId, savedEntity)`.
4. Return `ResponseEntity` with `201`/`200`/`404`, catching exceptions into `400` with the message, and
   `log.error(...)` via SLF4J.

`studyId` travels as a **`@RequestParam` on nearly every endpoint** — including GETs and DELETEs — because it
is the authorization scope. Keep that convention for new endpoints.

Base paths are inconsistent between kebab-case and camelCase (`/learning-process` vs `/studyOrganization`,
`/studyPersonnel`). Match the existing style of the resource
you touch. Renaming paths is fine — update `passport-web` and the Postman collection in the same change.

## Authorization

**Two independent mechanisms, both mandatory.**

1. **JWT validation** — `KeycloakSecurityConfig` registers the app as an OAuth2 resource server against
   `<auth-server>/realms/AI4HF-Authorization/protocol/openid-connect/certs` (RS256). CSRF disabled, CORS
   wide open. Endpoints are not secured by URL patterns; every controller checks explicitly.

2. **Per-study group membership** — `RoleCheckerService` → `KeycloakService`:
   - Creating a study creates a Keycloak group `study-<studyId>` with one subgroup per role, derived from
     the `Role` enum minus `ORGANIZATION_ADMIN` (`STUDY_OWNER`, `DATA_ENGINEER`, `DATA_SCIENTIST`,
     `SURVEY_MANAGER`, `QUALITY_ASSURANCE_SPECIALIST`, `DATA_STEWARD`).
   - `isUserAuthorizedForStudy(studyId, principal, allowedRoles)` returns true if the caller is a member of
     **any** of those subgroups for that study.
   - `isUserAuthorizedToViewStudy(...)` accepts any of the six non-admin roles.
   - `hasAnyRole(principal, roles)` checks **realm-level** roles instead — study-independent.
   - If the group is missing (deleted study) `KeycloakService` throws `410 GONE`; the frontend interceptor
     treats that specially by clearing the active study.

`Role` (`model/Role.java`): `STUDY_OWNER`, `DATA_SCIENTIST`, `SURVEY_MANAGER`, `DATA_ENGINEER`,
`DATA_STEWARD`, `QUALITY_ASSURANCE_SPECIALIST`, `ORGANIZATION_ADMIN`. Note `ORGANIZATION_ADMIN` is realm-only —
it has no per-study subgroup.

`KeycloakService` also owns user lifecycle (`createUserAndReturnId`, `updateRole`, `deleteUser`), study group
lifecycle (`createStudyGroups`, `deleteStudyGroup`, `assignPersonnelToStudyGroups`,
`removePersonnelFromStudyGroups`). Role names are always taken from the enum (`Role.X.name()`), never
written as string literals.

## Cascade-deletion validation

A hand-rolled dependency-graph traversal, not DB-level cascade reasoning. Every non-leaf resource exposes:

```
GET /{resource}/{id}/validate-deletion   →  200 + "Model,Passport"                   (safe, these cascade)
                                            409 + "Model"                            (caller lacks rights)
```

Implementation:
- `<Entity>Service.validate<Entity>Deletion(studyId, id, principal)` calls `validateCascade(...)` on each
  child service and aggregates via `ValidationResult.aggregate(...)`.
- `<Entity>Service.validateCascade(studyId, sourceResourceType, sourceResourceId, principal)` switches on the
  **parent's type name string** (`"LearningProcess"`, `"Experiment"`, `"Organization"`, …), finds affected
  rows, checks the caller's role for each, and recurses.
- Child services are injected with `@Autowired @Lazy` to break the circular dependencies this creates.
- `ValidationResult` is a record `(boolean status, String tables)`; `status=false` means unauthorized.

**When you add a foreign key you must add a `case` to the child's `validateCascade` switch and a call in the
parent's `validate*Deletion`,** or deletion will silently orphan rows.

## Audit logging & the passport

- `AuditLog` rows are written by controllers on every CREATE/UPDATE/DELETE, storing the serialized entity
  (`JSONUtil`) plus actor, study, timestamp, relation name and record id.
- On passport creation, `AuditLogBookService.createAuditLogBookEntries(passportId, studyId)` snapshots *all*
  audit logs for that study into the `audit_log_book` join table, freezing the change history.
- `PassportService.createPassport(PassportWithDetailSelection)` assembles `detailsJson` from ~16 optional
  sections driven by `PassportDetailsSelection` booleans (`isModelDetails`, `isStudyDetails`, `isDatasets`,
  `isFeatureSets`, `isLearningProcessDetails`, `isEvaluationMeasures`, `isModelFigures`, `isParameterDetails`,
  `isSurveyDetails`, `isPopulationDetails`, `isExperimentDetails`, `isLinkedArticleDetails`, …), then runs
  `cleanEmptyStringFieldsDeep` to either drop blank fields or replace them with `"N/A"` based on
  `isExcludeEmptyFields`.

  **Adding a section to the passport** means: a boolean on `PassportDetailsSelection`, a `fetchX(...)` private
  method, an `if` block in `createPassport`, a field on `PassportDetails`, and the mirrored frontend changes.

- `POST /passport/generate-and-sign` takes a `PdfRequest` (which names the `passportId`). The **first** call
  renders it with `PdfRenderService` (headless Chrome via `jvppeteer`, semaphore-limited, `pdf.*` properties),
  signs it with `PassportSignatureService` (EU DSS `PAdESService`, PKCS#12 keystore), and stores the signed
  bytes plus their SHA-256 on the passport row. Every later call returns those stored bytes instead of
  rendering again — a PAdES signature is timestamped, so re-signing would produce a different document and
  make the recorded hash meaningless.
- `GET /passport/{passportId}/signed-pdf` serves the stored document. `Passport.signedPdf` is `@JsonIgnore` +
  lazy, so listing passports never carries the bytes; `signedPdfHash` is exposed so a copy can be checked.
- `createPassport` chains the new row onto the newest passport of the same model (`version`,
  `previousPassportId`). Passports have no update endpoint by design.

> **The committed dev signing key expires on 2028-09-23** (self-signed `CN=AI4HF, O=AI4HF, C=NL`, alias
> `mykey`, password `password`, issued 2026-09-24). The same file is committed twice:
> `docker/deployment/keystore/keystore.p12` (mounted into the container) and `src/main/resources/keystore.p12`
> (local runs). After it expires, signing fails with "The signing-certificate ... is expired at signing time"
> and no PDF is stored. Regenerate once and copy the result over both files:
> `keytool -genkeypair -alias mykey -keyalg RSA -keysize 2048 -validity 730 -storetype PKCS12 -keystore
> keystore.p12 -storepass password -keypass password -dname "CN=AI4HF, O=AI4HF, C=NL"`.
> `PassportSignatureService` reads the keystore on every signing, so a running container picks up the
> replaced file without a restart; `dss.keystore.path`/`password` stay as they are.

## Data model

`docker/deployment/init-db.sql` is the source of truth (DDL first ~390 lines). The ER diagrams in
[`docs/data-model/README.md`](docs/data-model/README.md) are generated from it. Ownership chains:

```
Organization ─┬─ Personnel ─── (Keycloak user id)
              └─ StudyOrganization ─┐
Study ─┬─ Population ───────────────┤
       ├─ Experiment ─── FeatureSet ─── Feature
       ├─ StudyPersonnel (role)      │
       ├─ Survey                     │
       ├─ Parameter                  ▼
       ├─ LearningProcess ── LearningStage ── LearningStageParameter
       │     ├─ Implementation ── Algorithm
       │     ├─ LearningProcessParameter
       │     └─ LearningProcessDataset ── LearningDataset ─┬─ Dataset ─┬─ FeatureSet
       │                                                   │           ├─ Population
       ├─ LearningDataset                                  │           └─ Organization
       │                                DatasetTransformation ── DatasetTransformationStep
       ├─ Model ─┬─ ModelParameter                         (Dataset ── FeatureDatasetCharacteristic ── Feature)
       │  (previousModelId ── Model)
       │         ├─ ModelFigure
       │         ├─ LinkedArticle
       │         ├─ ModelEvaluation ─┬─ EvaluationMeasure
       │         │                   └─ ModelEvaluationDataset ── LearningDataset
       │         └─ Passport ── AuditLogBook ── AuditLog
       └─ AuditLog
```

Study-scoping is **not uniform** — worth knowing before reworking the model:
- Direct `study_id`: `Population`, `Experiment`, `Survey`, `Parameter`, `LearningProcess`,
  `LearningDataset`, `Model`, `Passport`, `AuditLog`.
- Indirect: `Dataset` (via `Population`), `FeatureSet`/`Feature` (via `Experiment`),
  `ModelParameter`/`ModelFigure`/`LinkedArticle`/`ModelEvaluation` (via `Model`),
  `EvaluationMeasure`/`ModelEvaluationDataset` (via `ModelEvaluation`).
- No study link at all: `Algorithm`, `Implementation`, `DatasetTransformation`,
  `DatasetTransformationStep`, `Organization`, `Personnel`.

Every FK is `ON DELETE CASCADE` except `study.owner → personnel.person_id`.

Composite-key join tables: `study_personnel`, `study_organization`, `feature_dataset_characteristic`,
`learning_process_dataset`, `learning_process_parameter`, `learning_stage_parameter`, `model_parameter`,
`audit_log_book`.

## Gotchas

- `io.passport.server.Passport` (Spring Boot main class) and `io.passport.server.model.Passport` (entity) share
  a simple name — always import explicitly and check which one a reference means.
- `spring.jpa.hibernate.ddl-auto=update` will happily leave dead columns behind. For renames/removals,
  update `init-db.sql` and wipe the volume (`docker compose down -v`) — don't write migration SQL.
- `init-db.sql` is ~616 KB; read it with `sed -n`/`grep`, not whole-file reads. DDL is lines 1–390.
- `Model.updateModel` currently does not copy `studyId`, and re-assigns `lastUpdatedBy` from the stale entity
  — a pre-existing quirk; several services have the same shape. Fix such quirks when they're in your path —
  nothing depends on preserving them.
- `pdf.chrome.executablePath` must point at a Chrome binary; in Docker it is `/usr/local/bin/chrome`.
- After a schema change, regenerate the ER diagrams with `python docs/data-model/generate_er.py`. A new
  table fails the run until it is placed in one of the script's `DOMAINS`.
